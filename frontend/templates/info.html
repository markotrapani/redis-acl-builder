🎯 What is Redis ACL Builder?

Redis ACL Builder is a comprehensive web application designed to help developers, database administrators, and security teams understand, test, and validate Redis Access Control List (ACL) rules before deploying them to production environments.

This tool provides an intuitive three-column interface that makes Redis ACL management accessible to both beginners and experts, offering real-time validation, interactive rule building, and comprehensive command testing capabilities.

🎯 Target Audience
  • Database Administrators - Configure secure access policies for Redis instances
  • Security Teams - Implement principle of least privilege access controls
  • Developers - Test application-specific Redis permissions during development
  • DevOps Engineers - Validate ACL rules before production deployment

📚 Redis ACL Basics

Redis ACLs control command and key access permissions. Rules follow left-to-right evaluation where later rules override earlier ones.

📝 Rule Syntax & Examples

Command Permissions

+@read # Grant all read commands
+@write # Grant all write commands
+@all # Grant all commands
+get +set # Grant specific commands

-@dangerous # Deny dangerous commands
-@admin # Deny administrative commands
-flushdb # Deny specific commands

Key Patterns

~* # Access to all keys
~user:* # Access to keys matching pattern
~cache:* ~sess:* # Multiple key patterns
~temp:[0-9]* # Numbered temporary keys
~data:? # Single character wildcard
~log:[a-z]* # Character range matching

💡 TIP: Use the Keyspace Tester to validate complex patterns like user:[0-9]*:session against actual key names before deployment.

🚀 Advanced Features

Advanced Key Permissions, Pub/Sub, Selectors & Examples

Advanced Key Permissions

# Read-only access to user:* keys
%R~user:*

# Write-only access to cache:* keys
%W~cache:*

# Read-write access to session:* keys
%RW~session:*

# Read commands + read-only key access
+@read %R~analytics:*

# Write commands + write-only key access
+@write %W~logs:*

Pub/Sub Channel Patterns

&* # Access to all pub/sub channels
&notifications:* # Access to notification channels
&events:* &logs:* # Multiple channel patterns

+@read +@pubsub &alerts:* ~data:* # Commands + channel + key patterns

⚠️ NOTE: Channel patterns (&) are parsed and preserved but cannot be tested in the UI. The app validates syntax but does not test pub/sub channel access permissions.

Rule Selectors

Selectors allow you to define multiple independent permission sets in a single ACL rule. A command is allowed if either the root permissions OR any selector grants it. Each selector creates an isolated permission context - commands granted by a selector can only access key patterns defined in that same selector.

# Basic Selector Syntax
+@read ~user:* (+@write ~logs:*)
# Root: Read commands on user:* keys
# Selector #1: Write commands on logs:* keys

# Multiple Selectors
+@all ~app:* (+@read ~analytics:*) (+@write ~logs:*)
# Root: All commands on app:* keys
# Selector #1: Read on analytics:* keys
# Selector #2: Write on logs:* keys

# Selectors with Advanced Key Permissions
+@all ~app:* (+@read %R~analytics:*)
# Root: All commands on app:* keys
# Selector #1: Read commands with read-only access to analytics:* keys

🔑 Key Concept: Selector isolation means each permission set is self-contained. In +@read ~user:* (+@write ~logs:*), GET can access user:* keys (root) but NOT logs:* keys (selector), and SET can access logs:* keys (selector) but NOT user:* keys (root).


📊 Selector vs. Key Permissions: Selectors (+@read ~key1) create mutually exclusive permission sets (choose one), while key permissions %R~key1 %W~key2 combine within the same set (mix and match). For multi-key commands like COPY, use key permissions (+@all ~dest:* %R~source:*) instead of selectors.


Complete Rule Examples

+@read ~* # Read-only user
+@read +@write -@dangerous ~app:* ~session:* # Application user w/ limited keyspace access
+@read +info +ping +client # Monitoring user
+@all -flushdb -flushall -shutdown # Developer access

🛡️ Security Best Practices

View Security Best Practices & Testing Guidelines

🎯 Principle of Least Privilege

  • Start with minimal permissions and add only what's necessary
  • Use specific command grants rather than broad category access
  • Implement key pattern restrictions to limit data access scope
  • Regularly review and audit ACL rules

⚠️ Common Pitfalls to Avoid

  • Overly Broad Access: Avoid +@all ~* unless absolutely necessary
  • Dangerous Commands: Always exclude -@dangerous for application users
  • Administrative Access: Restrict @admin commands to authorized personnel only
  • Key Pattern Validation: Test key patterns thoroughly to prevent unauthorized access

🔍 Testing & Validation

  • Use the Command Tester to verify Redis command permissions before deployment
  • Use the Keyspace Tester to validate key pattern matching with actual key names
  • Test glob patterns thoroughly: *, ?, [abc], [a-z], [^abc]
  • Test edge cases and boundary conditions for both commands and key patterns
  • Validate ACL rules in staging environments first
  • Document ACL rules and their intended use cases
